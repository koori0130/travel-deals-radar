## Context

專案目前是空的（只有 Spectra 設定）。需求是「旅行說飛就飛」：從台北 TPE、TSA 出發，看未來 1 年最便宜的目的地，以及未來 1 個月臨時釋出的超特價。討論結論：不做即時查詢，採每日快取；Google Flights 無公開 API，Amadeus 自助 API 已關閉，單一價格 API 抓不到航空公司快閃促銷，所以特價視圖必須直接納入航空公司促銷頁。

## Goals / Non-Goals

**Goals:**

- 每日產生一份價格快取與一份促銷快取，前端只讀這兩份檔案。
- 價格來源可抽換：先實測再選定，更換來源不需改前端。
- 第一批 5 家航空公司的促銷以統一格式呈現，並能看出哪個來源過期。

**Non-Goals:**

- 不做訂票、付款、會員。
- 不做全球任意目的地即時掃描；目的地限定設定檔內約 30 到 50 個。
- 第一版不接旅行社與比價站。
- 不抓取條款禁止自動抓取的網站。

## Decisions

### 前端與後端分離，以靜態 JSON 交接

前端是純靜態頁面（HTML、CSS、原生 JavaScript，不用框架），只讀 `data/fares.json` 與 `data/promos.json`。後端是獨立的命令列腳本，產出這兩個檔案。替代方案是前端直接呼叫第三方 API，但會暴露金鑰且受 CORS 與額度限制，因此不採用。

### 後端使用 Node.js

前後端同一語言，降低維護成本；抓取與排程腳本皆為 Node.js 命令列程式。替代方案 Python 也可行，但沒有明顯優勢。若實測階段發現所選 API 的官方 SDK 只有其他語言，再於 Open Questions 重新評估。

### 價格來源以轉接器介面隔離

定義一個轉接器介面：輸入（出發機場、目的地、月份範圍），輸出標準化的票價紀錄。第一個轉接器在實測任務後選定（候選：Duffel、Ignav）。替代方案是把來源寫死在管線中，但來源條款與可用性變動快（Amadeus 自助 API 已關閉即為例），所以需要可抽換。

### 促銷來源分三種取得方式

每家航空公司的來源設定檔註明取得方式：官方 feed、頁面抓取、人工補登。頁面抓取只在設定檔記錄「已確認條款允許」時才會執行。替代方案是一律抓頁面，但有條款與法律風險，因此拒絕。

### 特價判定以促銷頁為準，歷史中位數僅作輔助

一個月內特價視圖直接顯示「促銷中」的紀錄；價格 API 的歷史資料（至少 90 天）只用於年度視圖的輔助標示，歷史不足 90 天時不顯示折扣百分比。替代方案是兩個視圖都以歷史中位數低 30% 判定，但促銷頁本身已是特價，重複判定沒有意義。

### 失敗時保留舊資料並標示過期

單一路線或單一航空公司失敗時，保留上次成功的資料並標示過期時間，而不是清空。替代方案是整批失敗就不更新，但會讓所有資料變舊。

### 排程由 CI 定時工作執行

以 GitHub Actions 定時工作每日執行兩個命令並提交更新後的 JSON。這是建議值，尚未確認專案是否有遠端倉庫；命令本身與排程器無關，改用其他排程器不影響其餘設計。

### 查價連結導流，不嵌入或爬取第三方結果

2026-11-07 實測後新增。Google Flights 沒有公開 API 且不能嵌入，Skyscanner 的 API 只開放合作夥伴，爬取違反條款，所以頁面只產生預填路線與日期的 Google Flights 與 Skyscanner 連結，並提供 Google Flights 探索連結（依所選出發機場）。替代方案是引用兩站的搜尋結果，已拒絕。航空公司促銷若只有首頁網址，卡片明確標示為官網首頁、不帶查詢條件，避免讓人誤以為連到該筆促銷。

### 檢視狀態存於網址 hash

選取的分頁、機場、票種與航空公司寫入 URL hash（使用 history.replaceState，不新增歷史紀錄），重新整理或按返回後還原；hash 缺漏或毀損時回到預設。替代方案是只存在記憶體，但使用者從外部連結返回後會失去篩選。

### 促銷頁依航空公司篩選

促銷視圖提供航空公司複選，空選代表全部。年度視圖不提供：所選價格來源的最低價日期功能不支援指定航空公司（依 Ignav 文件，尚未實測）。

## Implementation Contract

**Behavior**

- `node scripts/fetch-fares.js` 讀取 `config/destinations.json` 與環境變數中的價格 API 金鑰，輸出 `data/fares.json` 並追加 `data/history/` 的每日紀錄。
- `node scripts/fetch-promos.js` 逐一執行 `config/promo-sources.json` 內的來源，輸出 `data/promos.json`；已過期促銷不出現在輸出中。
- `node scripts/add-promo.js` 接受人工促銷（欄位同標準促銷紀錄），輸出標記為 manual 的紀錄。
- 前端頁面 `web/index.html` 載入上述兩個 JSON，提供年度視圖與一個月特價視圖。

**Data shape**

- 票價紀錄：origin、destination、month、price、currency、tripType（oneWay 或 roundTrip）、taxIncluded、bookingUrl、stale、updatedAt。
- 促銷紀錄：airline、origin、destination、price、currency、tripType、taxIncluded、travelFrom、travelTo、saleStart、saleEnd（可為 null 表示未公告）、sourceUrl、fetchedAt、manual。
- `data/promos.json` 另含各來源的 lastSuccessAt 與 stale 旗標。

**Failure modes**

- 缺少金鑰：腳本非零結束，訊息指出缺少的環境變數名稱。
- 目的地代碼格式錯誤：查詢前失敗並指出該項目。
- 單一來源失敗：保留舊資料、標示 stale，其他來源照常輸出，結束碼為零但訊息寫入日誌。
- 前端讀取 JSON 失敗：顯示載入失敗訊息，不顯示任何票價列。

**Acceptance criteria**

- 腳本的單元測試涵蓋：標準化轉換、過期促銷剔除、stale 判定（3 天門檻範例）、部分失敗保留舊資料、金鑰缺少。
- 以固定的假資料 JSON 開啟前端，可驗證排序（Bangkok、Seoul、Tokyo 範例）、機場篩選、單程與來回分開排名、375 像素寬度無水平捲動。
- 規格 `fare-price-pipeline`、`airline-promo-feed`、`deals-explorer-page` 的每個情境都有對應的測試或手動驗證步驟。

**Scope**

- 範圍內：兩個管線腳本、人工補登腳本、設定檔、靜態前端、第一批 5 家航空公司來源、單元測試。
- 範圍外：訂票、帳號、旅行社與比價站、即時查詢、推播通知、全球目的地掃描。

## Risks / Trade-offs

- [價格 API 不支援想要的覆蓋或額度不足] → 第一個任務就實測候選來源，結果不理想時在此文件更新決策，轉接器介面讓更換成本低。
- [航空公司網站條款禁止自動抓取] → 逐家確認並記錄；不確定的改用官方 feed 或人工補登。
- [頁面改版使抓取失效] → stale 警示與保留舊資料，讓問題可見而不是無聲壞掉。
- [促銷價的單程、來回、含稅條件不一] → 欄位明確標示且前端不混排。
- [快取資料與實際可訂票價有落差] → 頁面顯示資料產生時間，並在說明文字註明以訂購頁價格為準。

## 任務 1.1 實測結論（價格來源）

標示「實測」的是 2026-11-07 以測試金鑰實際呼叫的結果；標示「文件」的只來自官方文件頁面，尚未呼叫。

**Duffel（實測，測試模式，讀寫權杖）**

- 一次呼叫只查一個出發日、一條航線：`POST /air/offer_requests?return_offers=true`，標頭 `Duffel-Version: v2`。TPE 到 NRT、BKK、ICN 與 TSA 到 HND 皆成功（HTTP 201），每次回傳 42 到 126 筆報價，耗時約 1.4 到 3.1 秒（實測，8 次呼叫）。
- 報價含 `total_amount`、`tax_amount`、`total_currency`，即含稅總價；幣別為 USD。
- 不指定目的地：失敗，HTTP 422，`destination` 為必填。
- 速率限制標頭顯示上限為 30（時間窗未實測）。
- 測試模式資料是模擬的：TPE 到 NRT 在 2026-12 與 2027-05 的最低價分別為 105.95 與 104.86 美元，幾乎不隨日期變動，且結果含虛構的 Duffel Airways；因此無法用它判斷真實票價是否可信。
- 沒有「某段期間每天最低價」的功能。涵蓋一年需要每條航線每個月至少取樣一個日期。
- 查超過約一年的日期只回傳 2 筆報價（2027-12-12 的測試），可見涵蓋範圍有限。
- 正式環境需要在儀表板按 Go live 並提供公司資訊（畫面所示），對個人專案是額外門檻；搜尋是否計費未確認。

**Ignav（文件，未呼叫）**

- `POST /api/fares/cheapest-dates`：一次呼叫回傳 1 到 31 天視窗內「每個出發日的最低價」，可單程或指定 `stay_days` 取來回價，價格含稅費，標頭 `X-Api-Key`。
- 需要 `origin` 與 `destination`，沒有不指定目的地的端點。
- 價格狀態為 `unverified`；文件未說明資料是即時或快取。回應不含航空公司與訂購連結，連結要另外呼叫 `booking-links`。
- 價格：每 1000 次成功請求 2 美元，附 1000 次一次性免費額度，無速率限制，開始時不需信用卡。

**結論**

- Duffel 不適合當作「最低價雷達」的主資料來源：單日單航線查詢、測試資料不真實、正式上線門檻高。
- Ignav 的 `cheapest-dates` 與需求最吻合，建議作為第一個轉接器，並以免費額度實測 TPE 與 TSA 的價格是否合理。
- 用量估算（估計值，未實測）：30 個目的地 × 2 個出發機場 × 12 個月視窗 = 720 次呼叫；每日全跑約 1.44 美元，一個月約 43 美元。降低成本的做法是近 2 個月每日更新、較遠的月份每週更新。驗證方式：以免費額度跑一輪並以實際呼叫次數換算。
- 任一來源都沒有「不指定目的地」的查詢，這與先前結論一致：第一版限定設定檔中的熱門目的地。
- 待辦：取得 Ignav 金鑰後，在任務 2.1 實測 `cheapest-dates` 並確認價格合理、是否含稅、資料新鮮度。
